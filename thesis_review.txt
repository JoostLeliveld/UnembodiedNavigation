# Deep Thesis Code Review

## 1. Thesis-Contribution Review
*Identify code that is actually part of the scientific contribution versus scaffolding, utilities, or experiment glue.*

### The actual scientific contribution:
The only genuinely novel mathematical machinery in this repository supporting the thesis is explicitly contained in:
- **`casadi_efe.py`**: The symbolic formulation of Expected Free Energy (`visibility_aware_unicycle_efe_ca`) that analytically bounds visual epistemic uncertainty through a planar homography observation model (`make_g_from_homography`). 
- **`base_planner.py` (`UnicyclePlannerBase`)**: The architecture linking the nonlinear control cost, the goal prior distributions, and the latent GP states.

### What should be ruthlessly cut or explicitly labeled as non-contribution scaffolding:
- **Custom GP implementation (`SimpleRBFGP`)**: The thesis is (presumably) fundamentally about active inference navigation under occlusion, *not* about creating a new numerical solver for exact Gaussian Processes. Keeping this custom math actively harms the thesis because an examiner will ask "how do we know your GP fits aren't numerically flawed?", dragging the defense down into linear algebra technicalities.
- **`yolo_selection.py`**: Custom polygon centroid processing and masking. There is zero thesis novelty here—this is pure YOLO post-processing scaffolding. It should use `shapely` or `cv2` exclusively so you are not defending hand-rolled geometry logic.
- **Data parsing and CSV manipulation**: Scripts like `plot_gp_and_ambiguity_maps.py` manually manipulate `np.asarray` arrays from CSVs. They should just use `pandas` or `xarray`, which drastically reduces the cognitive load of anyone auditing the visual metrics.

## 2. Plausible-But-Wrong Review
*Find every place where the code can return believable outputs while being wrong.*

**1. Mixing Logits and Probabilities on Plots**
- **Location**: `scripts/visibility_comparison/plot_gp_and_ambiguity_maps.py`
- **Issue**: For tracking uncertainty, the script plots `F_std_map` (latent standard deviation in unbounded logit space) if it's available, but silently falls back to `p_mean - p_map` (a compressed difference in `[0,1]` sigmoid probability space) if it isn't.
- **Risk**: They both draw a heatmap that visually looks like "uncertainty gradients", but the magnitude (`vmax=0.3`) is completely nonsensical when comparing logits vs bounded probabilities. You could publish a side-by-side comparison graph that compares two entirely different mathematical domains.

**2. Silent TF Transform Failures Corrupt Data Frames**
- **Location**: `src/experiments/experiments/nodes/experiment_logger.py` (`_latest_truth_pose`)
- **Issue**: If the TF tree momentarily drops (a common ROS 2 networking bug), the logger catches `TransformException` and silently returns `False, math.nan...`. 
- **Risk**: The CSV rows continue logging `NaN` for ground-truth accuracy. An averaging script downstream could compute metrics using `pandas.mean(skipna=True)`, making the robot's accuracy look phenomenal because the exact instances where it violently crashed or lost localization were the exact instances a TF dropped and it logged `NaN`.

**3. Silent GP Boundary Clamping**
- **Location**: `src/planning/planning/core/visibility_gp_map.py` (`_bilinear_map_np`)
- **Issue**: Coordinates querying the GP that fall outside the sampled bounds are silently clamped using `np.clip(ix, 0, self.xs.shape[0] - 2)`.
- **Risk**: If the robot explores outside the modeled bounds of the warehouse, the planner will confidently make decisions using the frozen, "extruded" probability border of the map. It looks like it's intelligently navigating, but it's hallucinating stale probabilities.

## 3. Numerical-Stability Review
*Look for instability, bad conditioning, and places where small numeric issues can corrupt results.*

**1. Masking True Mathematical Explosions in CasADi**
- **Location**: `src/planning/planning/core/casadi_efe.py`
- **Snippet**: `_logdet_small_pd` returns `ca.log(ca.fmax(det_val, 1e-12))`
- **Issue**: If the covariance matrix loses positive-definiteness due to a bad update or poor bounds (determinant goes below zero), `ca.fmax` artificially patches it to `1e-12` so `ca.log()` doesn't crash.
- **Risk**: The math is screaming that the covariance is collapsing, but the code effectively puts duct tape over it and passes `-27.63` (`log(1e-12)`) as the continuous cost. The optimization engine will keep sliding along this broken manifold instead of alerting you to a fundamental dynamics failure. 

**2. Naive Matrix Inversion inside Planner Risk Term**
- **Location**: `src/planning/planning/core/casadi_efe.py` (`risk_ca`)
- **Snippet**: `ca.solve(goal_S_pd, Sigma_pd)` and `ca.solve(goal_S_pd, diff)`
- **Issue**: `goal_S` strictly tightens down to `goal_prior_u_std_final` squared. As the goal variance shrinks aggressively, its condition number explodes. Directly using matrix inversion (`ca.solve`) on poorly-conditioned target covariances without robust generalized solvers or `eps` conditioning directly inside the `solve` block can blow up the L-BFGS-B gradient.

**3. Unsafe Custom Cholesky Decomposition**
- **Location**: `src/planning/planning/core/casadi_efe.py` (`_chol_2x2`)
- **Snippet**: 
  ```python
  l11 = ca.sqrt(ca.fmax(M[0, 0], eps))
  l21 = M[1, 0] / l11
  diag22 = ca.fmax(M[1, 1] - l21 * l21, eps)
  ```
- **Issue**: If `M[0,0]` happens to become exactly zero or negative (due to numerical precision), `l11 = sqrt(1e-9) = 3e-5`. Then `l21` gets divided by a tiny number, causing `l21` to explode massively. Then we do `M[1, 1] - l21 * l21`. Subtracting an exploding value from `M[1,1]` creates a heavily negative number. `fmax` clamps it to `eps`, completely vaporizing the information in matrix `M`. The Cholesky simply degenerates into noise without throwing an error.
