============================================================
0) Purpose and success criteria
============================================================
This plan focuses on finishing the current research stage with high confidence:

1. Scientifically valid comparison between MPC, EFE1, and EFE2 under the same dynamics and task setup.
2. Explicitly verified pinhole camera projection model and its impact on planning terms.
3. Reproducible experiments and plots with clear provenance.
4. A repository structure that supports later additions (new vision modules, RL policies, extra cameras) without rewriting core interfaces.

Primary outcome:
- A defensible results package (code + manifests + plots + interpretation notes) where each claim can be traced to a specific run configuration and mathematical definition.

============================================================
1) Current baseline assumptions (must be frozen before comparison)
============================================================
These assumptions are required for a fair comparison:

1. Same robot dynamics across MPC/EFE1/EFE2.
2. Same world and task initial conditions for each method.
3. Same state input contract (/state/bev + covariance).
4. Same control bounds and horizon.
5. Same process and observation noise values.
6. Same camera intrinsics within a comparison block.
7. Same random seed policy (or documented seed sweep protocol).
8. Same boundary/costmap treatment unless deliberately ablated.

If any of the above differ, the comparison is not method-only and results become harder to defend.

============================================================
2) Problem statement for this stage
============================================================
Research question for this stage:
- Under a fixed pinhole camera geometry and identical control constraints, what behavior differences arise between:
  a) MPC objective (risk + control only),
  b) EFE1 (first-order observation transform),
  c) EFE2 (second-order observation transform)?

Desired scientific claim:
- EFE2 should differ from EFE1/MPC specifically where projection curvature and uncertainty propagation matter, not because of unrelated implementation differences.

Method-definition lock (must hold for all reported comparisons):
1. MPC baseline in this repository is not a separate dynamics/controller stack.
2. MPC is defined as the same unicycle objective stack with:
   - add_ambiguity = false
   - same risk terms
   - same optimizer path/settings
3. EFE1 and EFE2 differ only in observation moment approximation (ET1 vs ET2), with all other terms fixed.
4. This stage evaluates approximation-quality effects (ET1 vs ET2) inside risk+ambiguity; it does not claim explicit mutual-information maximization unless that term is added later.

3) Critical math alignment tasks (highest priority)
============================================================
This is the core risk area. Implement these checks first.

3.1) Create a "canonical math spec" document in repo
File target:
- docs/math_efe_spec.md

Define exactly:
1. State definition and units:
   - z = [x, y, theta] or [x, y, theta, ...] as actually used per module.
2. Dynamics:
   - unicycle equations and Jacobian.
3. Observation model:
   - pinhole/homography mapping g(z), including whether theta appears in observation:
     - obs_mode=uv: y=[u,v]
     - obs_mode=uvt: y=[u,v,theta]
4. Risk term:
   - which space (state vs observation),
   - exact formula (KL Gaussian vs Euclidean proxy),
   - norm choice (L2, not L1) and why.
5. Ambiguity term:
   - exact quantity computed in code:
     Sigma_cond = Sigma_y - Gamma^T S^{-1} Gamma
     ambiguity = 0.5 * log|2*pi*e*Sigma_cond|
   - note: this is conditional-entropy-like ambiguity under Gaussian approximation of predicted observations, not explicit epistemic information gain (mutual information).
6. ET1, ET2, UT definitions and approximation assumptions.
7. Total objective:
   J = w_risk_state * risk_state + w_risk_obs * risk_obs + w_amb * ambiguity + w_u * ||u||^2 + w_bound * boundary

Acceptance:
- Every math symbol in plots and text maps to a concrete implementation location in code.

4) Camera model verification plan (pinhole correctness)
============================================================
4.1) Formal camera contract
Single source of truth:
- unav_common camera model module

Required invariants:
1. world_to_pixel and pixel_to_world are mutually consistent on Z=0 plane.
2. Homography H and H_inv produce bounded reconstruction error.
3. Frame convention is fixed and documented:
   - map_bev axes,
   - camera link frame,
   - yaw sign and angle wrapping.
4. Usable footprint is explicitly defined and enforced:
   - inside camera frustum,
   - Zc > Zc_min (recommended start: 0.3 m),
   - optional max range clip (recommended start: 10 m in map frame).

4.2) Verification scripts
Keep and standardize:
- scripts/verify_homography.py

Add tests:
1. Grid reprojection error:
   - sample N points in world footprint,
   - project world->pixel->world,
   - assert mean and max error thresholds.
2. Visibility boundary behavior:
   - points outside camera frustum should fail cleanly (NaN/out-of-view flag).
   - points with Zc <= Zc_min are treated as invalid for planner-comparison experiments.
3. Jacobian/Hessian sanity:
   - finite values where expected,
   - known growth behavior near geometric singular regions.

Acceptance thresholds (initial):
- Mean reconstruction error < 1e-3 m
- 99th percentile < 1e-2 m
- No silent sign flips in quadrant mapping

4.3) RViz + raw image confirmation
Goal:
- Always be able to show exact /external_camera/image_raw beside BEV overlays.

Checks:
1. RViz config uses Image Display (not Panel plugin).
2. Camera stream timestamped and synchronized with state logs.
3. One screenshot protocol for every run (camera + BEV view).

5) Planner comparison experiment design (MPC/EFE1/EFE2)
============================================================
5.1) Experimental factors
Fixed factors per batch:
1. world
2. task
3. camera intrinsics/extrinsics
4. dt, horizon, control bounds
5. noise parameters

Varied factor:
- planner method in {mpc, efe1, efe2}

Secondary factors (separate sweeps):
1. obs_mode in {uv, uvt}
2. state_source in {oracle, pixel}
3. pixel correction on/off
4. boundary_weight in {0, default}

Tertiary sweeps (required to expose ET1 vs ET2 differences):
1. Camera pitch sweep: {steep, medium, grazing} with all else fixed.
2. Initial belief scale sweep:
   - S0_scaled = alpha * S0_base
   - alpha in {0.25, 1.0, 4.0}

5.2) Required tasks/worlds for this stage
Minimum set:
1. One "near camera" task (e.g., y=-2 corridor)
2. One "far/grazing" task with stronger projection curvature
3. One diagonal task crossing varied depth/conditioning

Why:
- If only one easy geometry is used, EFE2 vs EFE1 may collapse and produce weak evidence.

5.3) Metrics to report
Trajectory metrics:
1. Success rate
2. Time to goal
3. Path length
4. Collision/constraint violation count

Estimation/uncertainty metrics:
1. Mean trace(S_state)
2. Mean trace(Sigma_y)
3. Mean ambiguity term
4. Terminal risk term
5. Approximation-difference isolators:
   - Delta ambiguity = ambiguity_ET2 - ambiguity_ET1 (evaluated on matched states)
   - Delta Sigma_y norm = ||Sigma_y_ET2 - Sigma_y_ET1||_F

Control metrics:
1. Mean |v|, |w|
2. Total control effort sum(||u||^2)

Camera geometry metrics (for interpretation):
1. Mean Zc along trajectory
2. Mean ||J|| and curvature proxy along trajectory

5.4) Plot set (paper-ready)
For each task:
1. XY trajectories overlaid (MPC/EFE1/EFE2)
2. Ambiguity and risk over time
3. Camera-space trajectory (u,v)
4. Side-by-side camera frame + BEV snapshot at key times
5. Aggregate bar/box plots across seeds

Rule:
- Every plot must include run_id and config hash in metadata or caption.

============================================================
8) Critical review checklist (sense-check before claiming results)
============================================================
Before claiming "EFE2 is better/different", verify all:

1. Same initial state and goal for all methods?
2. Same control bounds/horizon?
3. Same noise models?
4. Same camera parameters and frame conventions?
5. Any method receiving extra information (e.g., oracle state) while others do not?
6. Any stale data warnings in logs (pixel belief stale)?
7. Any reset-world timing artifacts affecting first seconds?
8. Any optimizer backend difference causing unfair speed/quality differences?
9. Any boundary penalty active for one method and not others?
10. Any run excluded post-hoc without pre-declared rule?
11. Any optimizer setting differences (maxiter, gtol, warm-start, backend) between methods?

If any answer is "yes", mark run batch as non-comparable.

12) Risks and mitigation
============================================================
Risk 1: EFE1/EFE2 difference too small in selected geometry.
Mitigation:
- Add tasks with stronger conditioning variation (depth and off-axis regions).

Risk 2: Numerical instability in covariance operations.
Mitigation:
- PSD projection + jitter with logging when activated.

Risk 3: JAX vs SciPy behavior divergence.
Mitigation:
- Benchmark both on identical snapshots; report objective and control deltas.

Risk 4: Hidden stale observation usage.
Mitigation:
- Enforce freshness checks and include stale counters in metrics/logs.

Risk 5: Plot misinterpretation.
Mitigation:
- Pair every qualitative trajectory figure with quantitative metric panel.
