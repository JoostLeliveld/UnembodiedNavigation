Runtime node graph
------------------
The important runtime chain is:

1. Gazebo world and external camera
   - launch: `src/sim/launch/bringup_sim.launch.py`
   - world: `src/sim/gazebo_worlds/worlds/warehouse_occ_light.world.sdf`
   - external camera model: `src/sim/models/external_camera/model.sdf`

2. YOLO detector
   - node: `src/perception/perception/nodes/yolo_robot_detector_node.py`
   - input: external RGB image
   - outputs:
     - `/perception/pixel_pose`
     - `/perception/detection_diagnostics`
   - semantic contract:
     - YOLO gives an image-space robot point and a raw detector score.
     - The point is usually taken from the bottom of the segmentation mask.
     - A bounding-box bottom fallback exists if mask use fails.
     - YOLO does not currently provide reliable visual yaw.

3. Pixel-to-BEV state
   - node: `src/state/state/nodes/pixel_to_bev_state_node.py`
   - core helpers:
     - `src/state/state/core/pixel_to_bev.py`
     - `src/state/state/core/noise.py`
   - output: `/state/bev`
   - semantics:
     - camera image point updates planar position `x,y`;
     - heading/yaw is odometry-derived;
     - this is a hybrid estimator, not a full visual pose estimator.

4. Goal publisher
   - node: `src/experiments/experiments/nodes/goal_mission_node.py`
   - publishes goal to `/goal_bev`.

5. Planner
   - runtime entry: `src/planning/planning/nodes/efe_agent_node.py`
   - main ROS wrapper: `src/planning/planning/nodes/unicycle_planner_node.py`
   - publishes intended commands to `/cmd_vel_raw` when command noise is enabled
   - publishes diagnostics such as `/planner_belief`, `/efe/metrics`, and `/planner/diagnostics`.

6. Actuation noise
   - node: `src/sim/sim/actuation_noise_node.py`
   - maps `/cmd_vel_raw` to noisy `/cmd_vel`
   - models command-space slip/noise, not lateral contact physics.

7. Experiment logger
   - node: `src/experiments/experiments/nodes/experiment_logger.py`
   - writes run data under `logs/experiments/...`.


Planner implementation
----------------------
Core planner:

`src/planning/planning/planners/base_planner.py`

This is the main implementation of the receding-horizon planner.
It handles:

- rollout evaluation;
- unicycle belief propagation;
- predicted image observation covariance;
- GP visibility queries;
- precision blending into `R_eff`;
- risk and ambiguity diagnostics;
- obstacle/workspace barrier;
- command extraction.

Symbolic objective:

`src/planning/planning/core/casadi_efe.py`

This builds the CasADi version of the EFE objective used by the optimizer.
It mirrors the cleaned paper semantics:

- reliability is clipped directly;
- `R_eff` is blended in precision space;
- there is no direct visibility reward, cost, or barrier.

Dynamics:

`src/planning/planning/core/dynamics.py`

This contains unicycle dynamics and process noise helpers.
Important caveat:

- planner process noise `Q` inflates the belief covariance;
- it does not add physical noise to Gazebo;
- physical command noise is modeled separately by `actuation_noise_node`.

Visibility map:

`src/planning/planning/core/visibility_gp_map.py`

This loads the offline GP artifact and provides planner-facing probability/reliability queries.

EFE math helpers:

`src/planning/planning/core/efe_utils.py`

This contains risk decomposition and related numerical utilities.

Obstacle/workspace guard:

`src/planning/planning/core/nogo_cost.py`

This is an engineering safety barrier, not the learned observability contribution.


Current paper-code semantics
----------------------------
The cleaned code no longer contains:

- `visibility_weight`;
- direct visibility rewards or penalties;
- visibility barriers;
- `efe_visibility` or `visibility_cost` logging;
- trust-shaping knobs such as `visibility_trust_low`, `visibility_trust_high`, `visibility_power`, or `visibility_trust_mode`;
- runtime optimizer route-family multistart seed knobs.

Therefore, do not describe the current main method as:

- adding a visibility reward;
- adding a shadow penalty;
- hard-constraining visibility;
- using runtime seeded route families.

Correct description:

The learned observability model changes the predictive detector-observation covariance `R_eff`.
This affects EFE risk, ambiguity, and predicted belief updates.

Offline rollout-family probes may still be used for diagnostics.
They are not the runtime optimizer unless the code is deliberately changed again.


Offline GP pipeline
-------------------
The learned observability field is built before runtime.
The planner loads a stored artifact; it does not fit a GP online.

Typical pipeline:

1. Capture detector observations:
   `scripts/visibility_comparison/capture_visibility_samples.py`

2. Extract detector targets:
   `scripts/visibility_comparison/extract_perception_targets.py`

3. Build heading-marginal GP targets:
   `scripts/visibility_comparison/build_gp_targets.py`

4. Fit GP artifact:
   `scripts/visibility_comparison/fit_visibility_gps.py`

5. Inspect GP and ambiguity maps:
   `scripts/visibility_comparison/plot_gp_and_ambiguity_maps.py`

Current intended GP target:

- sample robot at multiple planar positions;
- repeat over several headings;
- record raw YOLO score;
- average raw scores over headings at each `(x,y)`;
- clip the averaged score;
- transform with logit;
- fit an RBF GP in logit space.

Current main artifact path convention:

`logs/visibility_comparison/current_gp/yolo_score_raw_gp.npz`

Research implications
---------------------
The code is currently best interpreted as a paper-clean prototype for one central comparison:

constant detector-observation covariance `R0`
versus
learned state-dependent detector-observation covariance `R_eff`.

Important caveats for experiment design:

- `Q` is belief/process covariance inside the planner; it is not the same as physical disturbance.
- Physical command noise is modeled separately by `/cmd_vel_raw -> actuation_noise_node -> /cmd_vel`.
- YOLO confidence is an uncalibrated detector score, not a calibrated probability.
- The GP is 2D and heading-marginal.
- The estimator uses camera-derived position and odometry-derived heading.
- Solve time, callback timing, and pixel age can affect behavior and should be logged.
- Existing promising runs should be treated as preliminary unless rerun under the final cleaned experiment protocol.
