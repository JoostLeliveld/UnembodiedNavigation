# Missing active acceptance gates

This list is intentionally short and cross-module. Component findings remain in the
historical 66-row matrix and the generated successor matrix.

## Unassigned or incomplete acceptance ownership

1. **I14 documentation truthfulness is assigned to the coordinator and remains incomplete.**
   The historical audit lists exact contradictions in README, HOW_IT_WORKS, the runtime
   audit, registry, protocol and captions. Runtime repair completion must trigger a
   source-supported documentation pass. It must retain historical scopes and must not copy
   old values into the repaired path.
2. **Audit 15 owns independent executable cross-chain assertions; final orchestration is
   assigned to the coordinator.** The assertions join physical invocation/capture, detector outcome, camera
   observation, fused correction, stored terminal assimilation, belief revision, planner
   request/result, command receipt/application, odometry/contact, mission terminal status,
   logger drain and offline validator decision. The join needs owner-final IDs and schemas.
3. **The isolated physical command is deliberately absent.** Audit 14 owns the native guard
   wiring and private fixture. Acceptance requires source-bound evidence for clock loss,
   adapter/bridge loss, startup/shutdown zero, moving reset, contact health/positive probe,
   physical rest and terminal drain. Pure state-machine tests are insufficient.
4. **`source_batch_id` semantics need a visible versioned reconciliation with the requested
   acceptance wording.** The current producer uses `source_batch_id` for a logical
   all-camera cycle and unique `invocation_id` for one native predict/chunk. This can satisfy
   the underlying physical-invocation identity invariant only when each invocation occurs
   exactly once in explicit batch membership, the member IDs survive correction/outcome
   joins, and misses/silence/rejection terminate explicitly. `READY.json` must declare
   `logical_cycle_plus_invocation_v2` or `per_physical_invocation`; the final report must
   describe the schema correction rather than silently claiming literal per-call
   `source_batch_id` uniqueness.

## Evidence-level qualifications

- The GLOBAL route repair may pass its focused tests, but final acceptance waits for the
  coherent belief/goal/config/epoch token from 01/02 and the complete finite result contract
  from 08. Package-B LOCAL/direct age checks do not cover route mutation.
- Audit 02's expiry-side-effect concern is API/inspection evidence under the live single
  planning callback. It is not a confirmed active overlapping-solve failure unless the
  successor harness creates that supported interleaving.
- Old red probes assert defects. A failure of an old probe after repair is not a regression;
  desired-invariant tests must replace or invert it under a new source identity.
- Passing component counts cannot be summed and do not permit a simulator campaign.

The coordinator should keep these four responsibilities in the implementation tracker
until final acceptance records source-bound evidence for each one.
